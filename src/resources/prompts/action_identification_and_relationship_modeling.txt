# Clinical Workflow Extraction Prompt

You are extracting clinical workflow actions, control-flow dependencies, conditions, and temporal constraints from clinical text.

## TASK

Convert the input text into a workflow graph represented as JSON.

Extract:

- actions
- control-flow dependencies
- conditions
- temporal constraints

Follow the rules below strictly.

---

## ACTION EXTRACTION

An action is a single clinically meaningful activity that produces a clinical outcome.

The goal is to extract clinical activities, NOT grammatical verbs.

### Rules

- Extract one action for each clinically meaningful activity.
- An action may contain multiple verbs if they contribute to the same clinical intent.
- Do not split an action only because multiple verbs appear in the sentence.
- Prefer the largest text span that represents a single clinical activity.
- Preserve the order of appearance in the text unless explicitly stated otherwise.
- Action labels MUST be exact substrings of the input text.
- Do not normalize, summarize, or rephrase actions.

### Clinical Atomicity Rule

Different verbs belong to the same action if they contribute to the same clinical intent.

Different actions exist only when multiple independent clinical intents are present.

### Examples

"A diagnostic imaging study is performed using MRI"

→ ONE action

"a general clinical observation is requested to measure vital signs"

→ ONE action

"the patient receives dietary guidelines for proper adherence"

→ ONE action

"measure blood pressure and heart rate"

→ TWO actions

"perform ECG and administer aspirin"

→ TWO actions

### Non-Action Statements

The following statements do NOT generate actions:

- statements indicating that no action is required
- statements indicating absence of intervention
- statements indicating continuation of the current state without introducing a new clinical activity

Examples:

"no further action is needed"

→ no action

"no intervention is required"

→ no action

"continue as before"

→ no action

"maintain current management"

→ no action

Only extract actions that introduce a new clinical activity.

---

## CONTROL-FLOW DEPENDENCIES

Dependencies represent execution requirements between actions.

A dependency means:

> The target action can be executed only after the source action has been completed.

### Rules

- Dependencies represent precedence only.
- Do not assign dependency types.
- If an action follows another action, create a dependency between them.
- If multiple actions can start after the same predecessor, create one dependency from the predecessor to each action.
- If an action must wait for multiple preceding actions, create one dependency from each predecessor to that action.
- Do not create artificial join nodes.

### Dependency Minimization Rule

Create only dependencies that are explicitly required by the workflow.

Do not infer additional dependencies.

If two actions can occur independently, no dependency should be created between them.

### Examples

Sequential execution:

A1 → A2

Produces:

(A1,A2)

Parallel execution:

A1
├─→ A2
└─→ A3

Produces:

(A1,A2)
(A1,A3)

Synchronization after parallel execution:

A1
├─→ A2
└─→ A3

A4 waits for both A2 and A3

Produces:

(A1,A2)
(A1,A3)
(A2,A4)
(A3,A4)

---

## CONDITIONS

Conditions determine whether an action is executed.

Conditions belong to actions.

Conditions do NOT belong to dependencies.

Conditions are NOT actions.

Conditions are NOT temporal constraints.

### Condition-Action Separation Rule

Actions and conditions are mutually exclusive.

A text span identified as a condition MUST NEVER be extracted as an action.

Conditions represent:

- states
- findings
- measurement results
- clinical assessments
- decision criteria

Actions represent activities to be performed.

If a text span determines whether another action is executed, it MUST be extracted as a condition and not as an action.

### Condition Priority Rule

When a text span can be interpreted both as a condition and as an action, it MUST be interpreted as a condition.

### Computability Classification

For each condition extract:

- the exact condition text
- the computability class

#### COMPUTABLE

The condition can be evaluated automatically using structured values generated by previous actions.

Examples:

- blood pressure > 140 mmHg
- heart rate < 50 bpm
- glucose > 180 mg/dL

#### SEMICOMPUTABLE

The condition depends on results of previous actions but requires interpretation or classification.

Examples:

- ECG is abnormal
- imaging shows progression
- infection is suspected

#### NONCOMPUTABLE

The condition requires physician judgement or human assessment.

Examples:

- clinically appropriate
- physician considers necessary
- patient appears stable

### Rules

- Condition labels MUST be exact substrings of the input text.
- Conditions must never appear as actions.

### Exclusive Branching Rule

If multiple actions share the same predecessor and have different conditions, they represent mutually exclusive alternatives.

Example:

"If blood pressure is high, administer antihypertensive therapy. Otherwise monitor blood pressure."

The two resulting actions belong to different exclusive branches.

---

## TEMPORAL CONSTRAINTS

Temporal constraints specify when or for how long an action must be executed.

Temporal constraints are NOT conditions.

Conditions determine whether an action executes.

Temporal constraints determine when or how long an action executes.

### Temporal Constraint Types

#### REPEAT

The action must be repeated according to a frequency.

Examples:

- every day
- weekly
- every month
- every 6 hours

#### DURATION

The action must continue for a specified quantifiable duration.

Examples:

- for 30 minutes
- for 10 days
- for one week

#### OFFSET

The action starts relative to another event or action.

Examples:

- after 24 hours
- after one week
- within 7 days
- before surgery
- 3 days after discharge

### Rules

- Extract the exact temporal expression from the text.
- Temporal labels MUST be exact substrings of the input text.
- Temporal constraints belong to actions.
- Temporal constraints MUST NOT generate conditions.

---

## CONSISTENCY RULES

- Follow the order of the text unless explicitly overridden.
- Conditions and temporal constraints are distinct concepts.
- A text span cannot be both an action and a condition.
- A text span cannot be both a condition and a temporal constraint.
- Every condition belongs to exactly one action.
- Every temporal constraint belongs to exactly one action.
- Do not create artificial join nodes.

---

## REASONING PROTOCOL

Before generating the final JSON, internally execute the following steps.

### Step 1 - Identify Candidate Actions

Scan the text and identify all clinically meaningful activities.

For each candidate activity verify:

- Does it introduce a new clinical activity?
- Is it a clinically meaningful action?
- Is it not a condition?
- Is it not only a temporal expression?
- Is it not a non-action statement?

Discard any candidate that does not satisfy all requirements.

### Step 2 - Verify Clinical Atomicity

For each identified action:

- Merge verbs that contribute to the same clinical intent.
- Split actions only when independent clinical intents are present.
- Prefer the largest text span representing a single clinical activity.

### Step 3 - Identify Conditions

For each sentence determine whether a text fragment controls the execution of another action.

If yes:

- Extract the exact condition text.
- Associate the condition with the controlled action.
- Classify the condition as:
  - COMPUTABLE
  - SEMICOMPUTABLE
  - NONCOMPUTABLE

A condition must never be extracted as an action.

### Step 4 - Identify Temporal Constraints

For each action determine whether the text specifies:

- repetition frequency → REPEAT
- execution duration → DURATION
- temporal offset relative to another event/action → OFFSET

Extract the exact temporal expression.

A temporal constraint must never be extracted as a condition.

### Step 5 - Build Dependencies

Construct dependencies using execution requirements only.

For each action determine:

- Which actions must complete before this action can start?

Create one dependency for each predecessor.

Do not create dependency types.

Do not create artificial join nodes.

### Step 6 - Validate Workflow Consistency

Verify that:

- Every action label is an exact substring of the input text.
- Every condition label is an exact substring of the input text.
- Every temporal constraint label is an exact substring of the input text.
- Conditions are attached only to actions.
- Temporal constraints are attached only to actions.
- No condition appears as an action.
- No temporal constraint appears as a condition.
- No dependency has the same source and target.
- Action IDs are incremental.

### Step 7 - Generate Output

Generate the final JSON using only the validated actions, conditions, temporal constraints, and dependencies.

---

## OUTPUT FORMAT

Output ONLY valid JSON.

Do not output explanations.

Do not output markdown.

### Schema

```json
{
  "actions": [
    {
      "id": "A1",
      "label": "string",
      "condition": {
        "label": "string",
        "computability": "COMPUTABLE|SEMICOMPUTABLE|NONCOMPUTABLE"
      } | null,
      "temporal_constraint": {
        "type": "REPEAT|DURATION|OFFSET",
        "label": "string"
      } | null
    }
  ],
  "relationships": [
    {
      "from_action": "A1",
      "to_action": "A2"
    }
  ]
}
```

### Validation Rules

- Action IDs must be incremental: A1, A2, A3, ...
- Action labels must be exact substrings of the input text.
- Condition labels must be exact substrings of the input text.
- Temporal labels must be exact substrings of the input text.
- `from_action` cannot be null.
- `to_action` cannot be null.
- `from_action` and `to_action` cannot be equal.
